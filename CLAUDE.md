# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

HTML game prototype: a lab rat escapes a dark cardboard maze with a flashlight strapped to its back. All the code lives in `index.html` (inline CSS and JS, no dependencies, no build step); the only asset is the music in `audio/`. The only external resources are the Google Fonts fonts (Permanent Marker, Special Elite), with fallbacks. `concept/` holds the reference concept art (top-down view, cardboard walls with a corrugated edge, white rat with a harness) and the game doesn't load it.

The UI, the code comments and the README are in Spanish (Rioplatense, with voseo: "presioná", "escapaste"). Keep that tone.

## Run and test

There are no commands for building, linting or running tests. You open `index.html` in a browser, and with the built-in browser pane that's `preview_start` with `url: file:///C:/Claude/Laberinto/index.html`.

Quirks of the browser pane that affect testing:
- The page loads as a `data:` snapshot, so after each edit you have to navigate to the URL again.
- `requestAnimationFrame` is heavily throttled there, so simulated keypresses barely move the rat. To test logic, call the global functions directly from `javascript_tool`. Top-level `const` and `function` declarations are reachable from there. For example, `keys['arrowup']=true; for(...) update(1/60); render();`.
- `loadLevel(n)`, `startPlay()`, `resetRun()` and `castRays(x,y)` let you set up any situation. Setting `G.light=1` and calling `render()` gives you a lit frame for a screenshot.
- Mobile mode can't really be tested in the pane, because with the local file touch emulation doesn't trigger on reload. Add the `touch` class to the `body` and simulate the finger with `PointerEvent` (`pointerdown`/`pointermove`/`pointerup`, using the same `pointerId`) on `#stickZone`. Final testing is on a real phone, at the Pages URL.
- The canvas can be 0×0 when the page loads, so `resize()` keeps it at least 1 px. In `frame()`, `requestAnimationFrame` is scheduled before `update`/`render` so that an exception doesn't kill the loop.

## Script architecture (`index.html`)

**Tunable constants** at the top: `C` (cell size, 64 world units), `T` (wall thickness), `K` (apparent wall height), speeds, `LIGHT_R`/`CONE` (flashlight), `RAYS`. Progression comes from `SIZES`/`sizeFor(n)` (maze columns×rows), `viewCells(n)` (how many cells across fit on screen, i.e. the zoom, which gets closer with each level) and `timeFor(n, pathCells)` (time limit from the shortest path length).

**Maze** (`genMaze`): recursive backtracker on a W×H grid. Walls are stored as `hW[r][c]` (top wall of row r) and `vW[c][r]` (left wall of column c). The entrance is always on the right side (`entRow`) and the exit on the left (`exitRow`). From level 2 on, some walls are removed to create cycles. Everything is seeded with `mulberry32(G.baseSeed + n*7919)`. "Retry the same level" relies on not regenerating: `resetRun()` only repositions the rat and resets the timer.

**Geometry** (`buildRects`): walls are turned into rectangles (collinear runs merged, plus a start pen outside the entrance). That single list `G.rects` is used for collision (circle vs rectangle, two circles: body and head), for ray casting, and for drawing. `buildDeco` adds purely visual elements: sheet seams, floor tape and pencil marks, which work as landmarks.

**Rendering pipeline** (`render`). This is the core of the visual look and needs care when you touch it:
1. Fully lit scene: floor (`drawFloor`, using a tiled texture pattern) on the main canvas, and walls (`drawWalls`) on `wallCv`. For the 3D effect, each wall's top face is the base rectangle scaled by `(1+K)` around the camera, and only the side faces facing the camera are drawn.
2. Light map: `castRays` fires `RAYS` rays from the flashlight against the wall edges (all axis-aligned) and gets a visibility polygon. On `aCv` the beam sprite (`coneCv`, generated pixel by pixel at startup) is drawn, clipped with `destination-in` to that polygon. That's the floor light. On `bCv` the same beam is clipped to a polygon extended by `T+6` (plus its version projected by `(1+K)`) and to the shape of `wallCv`, so the top faces and sides of the walls get lit. Both are added (`lighter`) into `lightCv` over black.
3. `multiply` of `lightCv` over the scene: anything without light stays fully black. "Total darkness" is a design decision: lit areas are not remembered. Before it's added to `lightCv`, the floor light goes through `blurCv` (half resolution, `ctx.filter = blur`) so the shadows have a soft edge (`SHADOW_SOFT`). If the browser doesn't support `filter`, it falls back to hard shadows.
4. The rat (`drawMouse`, procedural) and the lens glow are drawn after the darkness, so they're always visible. The rat is drawn opaque in its own canvas (`mouseCv`, only in a rectangle around it) and darkened with `source-atop` based on the light. Don't use `globalAlpha` to dim it: it becomes see-through and its overlapping parts show through.
5. The walls are taller than the rat, so they get drawn again on top of it, already lit (`wallCv × lightCv`, built in `litCv`), but only in a rectangle around the rat.
6. Iris wipe: a black circle centered on the rat. Before it, `exitDarkness()` darkens the light and the rat while it crosses the exit threshold (exit row only). It closes when you go through the exit, and the win card appears once it's closed (`showWinCard`). It opens in `startPlay`. Its state is `G.iris` (1 = open) / `G.irisTarget`, and it takes `IRIS_T` seconds.

The wall light (`bCv`) is also blurred (`WALL_SOFT`) before being clipped to the shape of the walls, so the edge of the lit area on the wall tops doesn't look like a hard circle. Camera shake (`G.shake`) builds up when you bump several times in a row (less than 1.2 s apart). It only offsets the camera while drawing (`render` adds it to `cam` and takes it back off at the end).

The cards (`card()`) are animated: the one leaving shrinks (`.out`, 0.13 s) and the next one appears small and grows with a bounce (`.in`). `pop(el)` does the same for HUD stickers (level and timer when a level starts).

**Rat animation**: everything is drawn in `drawMouse` in local coordinates (+x = forward, from x≈-20.5 at the rear to x=18 at the tip of the snout). Its anatomy follows a reference the user sent. The body and head are a single pear-shaped `Path2D` silhouette (wide at the back, pointed at the snout), and the harness is clipped to it. The ears are ovals that grow backward from the sides of the head, with the pink inside shifted toward the body. They're tilted outward by `EAR_TILT`, with the pivot at their back base on the body side. The eyes sit close to the snout, red with a white highlight; closed, they're a short sideways line curving toward the back. The whiskers start next to the nose and fan out to the sides. The paws sit slightly under the body, with fingers pointing forward and outward: the front ones are beside the eyes, in front of the ears, and the back ones are at the hips. The flashlight on its back (inspired by a hand flashlight the user sent: bluish-gray body, yellowish COB panel) has a battery bar that shows `timeLeft / timeLimit`. It drains toward the tail, turns orange below 25% and red below 10%, and blinks in the last 10 s. The head and lens of the flashlight (x 4..8.6) shouldn't be changed: the user likes them as they are. When it bumps into a wall, `hx()` compresses everything in front of the shoulders (the head pulls back) and `updateTail` adds a quick tail wag. The head turns on the neck (`NECK`, `M.headA`): the silhouette bends gradually (helper `P`) and the face (nose, ears, eyes, whiskers) rotates as a whole. It leads into the turn, and when idle `animMouse` sometimes makes it look to one side, or to one side and then the other, before returning. The tail is the exception: it's a chain of `TAIL_N` points in world coordinates (`M.tail`, computed in `updateTail`). Each point moves toward a rest shape (a ripple tied to `M.phase`, a sway tied to `G.time`, and a curl tied to `M.turnV`), keeps the segment length fixed and is pushed out of the wall rectangles, so it never goes through walls. `resetRun` sets it to `null`, which rebuilds it. `animMouse()` drives the gestures: the bump against a wall (`M.bumpT`: ears flap, whiskers tremble, eyes close), the random blink (`blinkT`), and the left or right ear twitch (`twitch`), which only happens after a second without input.

**States** (`G.state`): `title` → `intro` → `play` ⇄ `paused` → `won` | `dying` → `lost`. The cards are HTML (`#card`), and the HUD (level, timer) is DOM over the canvas. The canvas is `position: fixed; inset: 0` and its size comes from `clientWidth`/`clientHeight`. Don't go back to `100vh`: on phones it includes the browser bar and pushes the camera off center. After following the rat, the camera keeps it inside `safeZone()`: 15%–85% of the screen, and on mobile between the bottom of the HUD and 72% of the height (so it doesn't end up under the HUD or under the finger using the joystick). When time runs out, the light flickers and goes out (`dying`) and you go back to the start of the same maze. The camera (`camTarget`) follows the rat with some lookahead and is clamped to the maze edges when the maze is larger than the screen.

**Input**: directional control on both platforms, with no tank controls (the user tried them and changed their mind, and the gyroscope was dropped too because it was uncomfortable). Each frame, `update()` computes a target direction on screen. It comes from the floating joystick on mobile (`Stick`, with `#stickZone` covering the screen and the base `#stick` appearing where you put your finger) or from the arrows/WASD on PC (↑ = up, and they combine into diagonals). The rat turns toward that direction gradually, limited by `TURN`, and moves at `SPEED × magnitude × cos(angle difference)`, so it first turns and then moves forward. Space, click or tap trigger `primaryAction()`. Mute is saved in `localStorage` (`raton.muted`).

**Sound** (`Snd`): the effects are all synthesized with WebAudio (oscillators and filtered noise, no files), including the "whoosh" of cards entering (`cardIn`) and leaving (`cardOut`). `Snd.init()` runs on the first keypress because of the browsers' autoplay policy. The music is the only file: `audio/laberinto-de-circuitos.mp3`, in `Music` (an `Audio` element on loop, separate from WebAudio). It starts on the first tap or keypress (already on the title screen; browsers don't allow audio before a gesture), fades in to a low volume (`Music.vol`, so it doesn't drown out the effects), and pauses and resumes with the pause. Music and effects have separate buttons and mute states (`raton.musicMuted` / `raton.muted` in `localStorage`; keys M / F). In the browser pane the mp3 doesn't load, because the local file opens as a `data:` snapshot. Test it at the Pages URL.
